# first-agent · 从生活念头到第一个 AI 助理

**给谁用**：想搭自己的第一个 AI 助理但不知道从哪下手的人。
**做什么**：AI 引导你把一个模糊的生活念头，挖成能真正跑起来的第一个 Agent——然后陪你不断从生活里长出更多。

这套方法来自一个真实跑着的 15-Agent 个人助理系统（情报/求职/素材/时间/读书/记账/情绪……各管一摊，每天真的在被使用）。它不是理论，是**从实战倒推出来的流程**。

## 0. 一句话

**大多数人做 Agent 失败，不是因为技术不行，而是跳过了「这东西到底解决我生活里哪个具体问题」这一步。**

三个最常见的死法：
- ❌ 从一个想法直接开干 → 做出两周就吃灰的玩具
- ❌ 先建系统再找用途 → agent 互相聊天，没有一个真被用
- ❌ 需求靠脑补 → 做完不知道「什么算做成了」

正确顺序是**反过来**：从生活里已经冒出来的念头出发 → 确认它是真需求 → 才动手。

## 阶段一 · 抓念头（Signal Capture）

用户说「我想做个 XX agent」时，AI **先不要动手**，走这四问：

1. **这个念头是从哪来的？**（一句话/被某件事烦到/看到别人有/突然想到）
2. **它出现过几次了？**（第一次冒出来 / 想过好几次 / 天天都在想）
3. **没有它，你现在是怎么凑合的？**（手动做 / 忍着 / 干脆不做）
4. **如果明天它就消失了，你会难受吗？**（会 / 不会 / 说不好）

**判定规则**（诚实执行，不奉承）：

| 信号 | 判定 |
|---|---|
| 出现 ≥3 次 / 天天在凑合 / 消失了会难受 | ✅ **真需求，进入阶段二** |
| 第一次冒出来 / 现有方式还能凑合 | ⏸ **先放进「念头仓库」，别做**。跟用户说：这个先记下来，两周后再看还想不想做 |

**为什么这么严**：做过个人助理系统的人都知道，最大的成本不是写代码，是**做完没人用**。念头仓库是防吃灰的第一道闸。

### 念头仓库（简单文件即可）

```markdown
# 我的念头仓库
| 日期 | 念头 | 出现次数 | 状态 |
|---|---|---|---|
| 2026-XX-XX | 想要一个帮我盯快递的 | 1 | ⏸ 观察 |
| 2026-XX-XX | 每天早上想知道今天该干嘛 | 5 | ✅ 升级为候选 |
```

## 阶段二 · 挖需求（Clarify · 5 步）

真需求确认后，AI **逐条问**（一条一条等回答，不要一口气全问）：

### 1. 定对象
> 「这个 agent 的产出，最后是**谁**看/用？他拿到之后**做什么动作**？」
>
> ⚠️ 如果答案是「我自己看看」→ 追问：「看完之后你会改变什么行为吗？」如果什么都不改变，这个需求不成立。

### 2. 定范围
> 「它管什么、不管什么？第一版只做哪一件事？」

**铁律：第一版只做一件事。** 「帮我管理生活」不行，「每天早上告诉我今天有什么事」可以。

### 3. 定频率
> 「这是一次性的，还是每天/每周都要的？什么时间点需要它？」

**一次性需求不需要 agent。** 这是很多人绕的弯——为了发一条朋友圈搭了一套系统。

### 4. 定产出形态
> 「你希望它怎么找到你？一条消息？一张卡片？一份文档？在哪个平台（微信/飞书/终端）？」

**原则：往你已经在看的地方推**，不要造一个「要去专门打开看」的新入口。

### 5. 定验收 ⭐最重要
> 「怎么做算它做成了？给我一个具体的场景：什么时候、发生什么、你会觉得『还好有它』？」

**没有验收 = 没有止损线**。写下来，例如：
> 「每天早上 8:30 我打开手机，能看到今天 3 件最重要的事和它们的时间」——连续 7 天都做到 = 及格。

### 收口：任务书

五问问完，AI 把答案收口成一段**任务书**（用户确认后才动工）：

```markdown
# <Agent 名> · 任务书 v1

**目标**：<一句话>
**对象**：<谁用，用来做什么动作>
**范围**：<只做这一件事>（明确不做：<列举>）
**频率**：<每天 X 点 / 每周 X / 事件触发>
**产出形态**：<消息/卡片/文档，推送到哪里>
**验收标准**：<具体场景 + 数字>

**分界线**：
- AI 做：<自动化部分>
- 人做：<判断/拍板部分>
```

## 阶段三 · 建 Agent（Build）

### 3.1 先写 agent.md（三件套，缺一不可）

```markdown
# <Agent 名>

## 做什么
<从任务书抄，只写验收标准里要求的>

## 不做什么 ⭐最重要
<明确列出边界>
- 不<越界的事 1>
- 不<越界的事 2>

## 和谁协作
- <上游：数据/信息从哪来>
- <下游：产出给谁/推到哪>
```

**为什么「不做什么」最重要**：没有边界的 agent 会慢慢长成什么都想干的杂物间，最后哪个都干不好。实战系统里每个 agent 都有明确的一亩三分地。

### 3.2 最小实现（MVP 原则）

- **先跑通一次**：哪怕人肉触发、哪怕只有一条消息，先让它真的运行一次
- **跑通 ≠ 做完**：第一次跑完就问用户「这个形态你每天都会看吗？」——不会就改形态，别急着加功能
- **稳定 7 天再加功能**：连续 7 天按验收标准跑，用户还在用，才进入下一轮

### 3.3 技术选择（按用户现有环境问）

> 「你平时用的是什么工具/平台？」——不要推荐用户学新东西，**用他已有的**：
- 已有 Claude Code / Codex → 最简：一个 SKILL.md + cron 触发
- 已有 Hermes → profile + SOUL.md + cron
- 什么都没有 → 从「一个 prompt 文件 + 手机备忘录手动触发」开始也行，**先有流程再有工具**

## 阶段四 · 养起来（Grow）

第一个 agent 跑通后，**禁止立刻规划「我的完整 agent 体系」**。

正确的生长方式：

### 4.1 念头仓库持续进货
生活中每个新念头都丢进阶段一的仓库，标日期和次数。**让信号自己攒够**，而不是想一个做一个。

### 4.2 升级判定
一个念头满足任一条即升级：
- 出现第 3 次
- 开始占用你注意力（你发现自己在手动做它）
- 别人也开始问你要

### 4.3 第二个 agent 的产生方式（推荐顺序）
1. **从第一个 agent 的「不做什么」清单里长出来**——那个边界里的某条，值得单独一个 agent
2. **从第一个 agent 的用户习惯里长出来**——用户开始在 agent 输出上做后续动作，那个动作就是新 agent
3. **从生活新需求里长出来**——走完阶段一、二全流程

### 4.4 多 Agent 的本质
**不是并行，是分工与边界。** 每个 agent 一亩三分地，跨 agent 的事走明确交接（谁发起、谁接收、怎么确认完成）。

**判断「该不该拆成两个 agent」**：如果两个职责的**节奏不同**（一个每天跑、一个事件触发）、或**失败影响不同**（一个挂了不影响另一个）→ 拆。否则合并。

## 反模式（AI 必须主动阻止用户）

| ❌ 用户说 | ✅ AI 应该说 |
|---|---|
| 「我想做一个万能助理」 | 「先说一个这周让你烦过的具体场景」 |
| 「帮我搭一套多 agent 体系」 | 「先说第一个：哪个单点需求最痛？」 |
| 「我想到一个好点子」（第一次） | 「记进念头仓库，两周后再看」 |
| 「能不能加上 XX 功能」 | 「第一版验收标准里有它吗？没有就记到 backlog」 |
| 「怎么这么慢，能不能一口气全做完」 | 「跑通一次比做完更重要——先让它今天真的发一条消息」 |
| 「要不要也做个 XX？别人都有」 | 「别人的需求不是你的需求。你的念头仓库里有它吗？」 |

## 移植注意

本 skill 只依赖「能对话」。各阶段产出的文件（念头仓库/任务书/agent.md）存到用户方便的地方即可。

- **Hermes**：每个 agent 一个 profile + SOUL.md；定时用 cron
- **Claude Code**：SKILL.md + hooks / launchd / cron
- **其他平台**：文件 + 对话即可，定时用平台自带机制
