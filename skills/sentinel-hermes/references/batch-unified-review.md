# 批次统一整理：多条录音 → 一个工程视图

适用：一次录了多条同主题录音（比如连续几条都在讲同一件事），说「帮我统一整理」。产出不止是逐条档案，还要一份把 N 条想法串起来的总览。

## 1. 判定「这 N 条是一个工程」而不是 N 个待办

三个信号，越多越成立：

- **名词复现**：多条录音反复回到同一个对象（例：迁移 / 索引 / 目录结构）。
- **依赖措辞**：出现「先……再……」「要……就得……」「没做的话后面做不了」——说明条与条之间有顺序。
- **递进修正**：后一条在扩展或修正前一条的方案（例：第一条说要迁移 → 第二条说迁移前要先落实方案 → 第三条说迁移后还要解决协同协议）。

只有名词复现、没有依赖和递进的，多半是并列的独立想法，不要硬凑成工程。

## 2. 切层次（工程天然分层）

先给每条录音标一个「它在这件事里管哪一层」，再把同层的合并。常见四层（示例，按实际内容切）：

| 层 | 管什么 | 典型信号 |
|---|---|---|
| 结构层 | 文件/目录/归档怎么摆 | 迁移、拆分、分类、索引 |
| 协同层 | 多个角色/工具怎么配合 | 谁负责哪块、新内容怎么被感知、跨库怎么写 |
| 认知层 | AI 怎么懂用户、输出怎么像样 | 上下文、风格沉淀、约束规则、反馈迭代 |
| 资产层 | 有价值的东西怎么存成可检索的 | 合并旧库、索引层、别成垃圾箱 |

目标/动机通常不占一层——它贯穿所有层。把动机抽出来单独写成一条线，比塞进某一层更清楚。

## 3. 标前置闸门

找明确说了「必须先做完 X 才能做 Y」的句子，那就是闸门。闸门决定了建议顺序：**闸门没通的动作全部往后排，先做那些不依赖闸门的**。

在总览里要写明闸门，否则执行的人会直接去动文件。

## 4. 总览文档骨架

```markdown
---
date: YYYY-MM-DD
type: 灵感
source: N 条妙记统一整理（录音时间范围）
keywords: [...]
note: 本文件不是单条妙记的档案，而是 N 条录音的统一整理，串成一个大工程视图
---

# 大工程总览：<主题一句话>

> 来源：N 条妙记（起止时间）
> 原始逐条档案：archive/YYYYMMDD_*.md（N 份）

## 一、这个工程到底是什么        ← 一段话讲清母题 + 层次表（层/目标/关键动作/来源录音）
## 二、L? 具体层               ← 每层一节，写「要干什么 + 具体动作编号 + 卡点」
## 三、前置依赖（卡点）          ← 闸门单列，引原话
## 四、目标线（动机）            ← 贯穿所有层的那条线
## 五、并行小项目                ← 表格：项目 / 动作 / 来源
## 六、零碎提醒                  ← 表格
## 七、建议的下一步顺序          ← 按闸门排序，先做不依赖闸门的
```

## 5. 保真红线

- 层次划分、闸门判定、动机抽取都是**你的分析**——可以在总览里明确写成「我的判断」，但引用的原话、待办、数字必须来自转写原文。
- **不能因为「听起来像一个工程」就把转写里没提的步骤写进下一步**——下一步里的每一步都要能指回某条录音的原话或明确标注「待用户确认」。
- 没识别说话人的段落标「未识别说话人」，不猜。
- 涉及他人产出的素材要标归属，不算录音主人的产出。
- 总览里的待办同样只记本地 TODO.md / 档案，**不建任何外部任务卡**。

## 6. 收尾

0. **先核对上一批是否已处理完再开新批**：同一工程跨天分批到时，可能上一批还没归档——开新批前用 `scripts/find_unprocessed_minutes.py` 看有没有欠账，有就先补完再开始新批，免得同一主题的档案分散在两套未合并的产出里。
   - **批量搜未处理 token 时必须分段拉 `+search`**：只拉第一页会把当天早先录的稿整批漏掉——实测一次拉回 15 条 vs 分段拉回 42 条，差的全是当天早上的。且 API 在 50 条处硬截断、`has_more=false` 不可信，按天分段切。
   - **写档案前查同名**：不同批次的同名稿会撞名覆盖。写前 `ls` 目标名，已存在且 token 不同 → 加后缀改名。写完校验全库 token 无重复。
1. **逐条档案 + 总览文档全部写完后，先跑 fact_check 校验，再更新 state.json。** 每份档案都要过：`python3 <skill目录>/scripts/fact_check.py <档案路径> --source <合并源文件>`，exit=0 才许登记；exit=1 按输出逐条修后重跑。**批量归档时这一步最容易漏**——一次写 15 份就以为「格式一样没问题」，结果 15 份全带着同一个 P0。**批量场景把 fact_check 写成一个循环跑完 15 个文件，全绿再动 state.json**，不要逐个手点。
   - 合并源文件 = 「妙记元信息头（token/title/开始时间/时长毫秒）+ 逐字稿原文」拼一起，头写 token/title/开始时间/时长毫秒，正文逐字稿零改动。**不要传裸 transcript.txt**（token 里的长数字会被当成编造数字判 P0）。
   - 批量场景必踩的两个 P0（除非校正，否则整批不合格）：
     - **缺一级标题**——frontmatter 之后必须有 `# 标题`（标题取文件名 slug），只有 `## 三句话摘要` 会被判「无一级标题」。
     - **交叉引用写完整文件名**——总览文档里写 `YYYYMMDD_灵感_主题A.md` 这类文件名，其中的 8 位日期数字在逐字稿里找不到 → 判编造。改成「同批录音里的「主题A」那条（见归档目录下同日档案）」。同理正文里的具体日期+时刻（如「YYYY-MM-DD 06:52 提出」）逐字稿里没有 → P0，时间用「录音时间 XX:XX」表述。
     - 引用转写时间戳用秒级（`[00:04:15]`），不写小数部分（`15.700` 会被切成找不到的数字）。
2. 全部通过后才更新 state.json（processed 只放纯 token 字符串，总览写「（总览）」行 + 各 token 行）。
3. 跑一次 `scripts/scan_minutes.py` 确认不重复报。
4. 汇报只给结论：N 条已归档 + 总览文档路径 + 需要用户拍板的点（闸门是谁、方案二选一选哪个）。
