# 哨兵实战坑位清单

> 每一条都是真实线上事故或实测发现。**这是本 skill 与通用教程的区别所在** —— 通用教程只说「怎么做」，这里说「不这么做会死」。
> 格式：⚠️ = 真实事故/教训（踩过坑导致漏扫、重复归档、误判、编造）；其余 = 实测确认的边界条件。
> 本版本只做扫描 + 归档，所有规则都不涉及通知与外部系统。

---

## 一、搜索与分页

### ⚠️ 1. 大窗 + 翻页会漏整段（最隐蔽的漏扫）
- **现象**：72h 窗配 `--page-token` 翻页拉了 50 条，`has_more=false` 显示「拉全了」，实际**中间一整天（20 条）完全没出现**。起点明明覆盖它。
- **正确做法**：**按天分段查**（每天一窗 + 段内翻页），再按 token 聚合去重。这是唯一可靠的拉法。72h 窗改按天后，4 天拉到 99 条无缺。

### ⚠️ 2. `+search` 在 50 条处硬截断，`has_more=false` 是假的
- **现象**：整窗拉 30 天，无论 `--page-size 15` 还是 `30`、翻多少页，API 一律只给 50 条；`has_more` 在第 4 页（15 条版）或第 2 页（30 条版）就变 `False` —— 看着「翻页拉全了」，实际漏 35+ 条。
- **截断丢的是「最早」的那批**（结果按时间倒序返回）。对「找新稿」影响小，对「回扫历史欠账」是致命的 —— 永远只能看到最新 50 条。
- **正确做法**：宽窗复查必须**分段拉**，段长由「每段实际返回 < 50 条」倒推（不是按固定天数切）。录音密集的账号 4 天一段仍超 50；12h 一段扫 30 天（186 条）才捞出漏档。
- **判据**：单窗口返回条数**恒等于 50** = 截断信号。

### ⚠️ 3. 分段扫描必然撞 API 限流
- **现象**：30 天 / 12h 一段 × 60 段 × 2 轮 = 120 次 `+search` 调用。段间无 sleep → **21 段挂在 `99991400 request trigger frequency limit`**。挂掉的段等于没扫。
- **正确做法**：三件套 —— ① 段间 sleep 2.5 秒 ② 失败指数退避 4→8→16→32→64 秒、最多 5 次 ③ 每段成功后写进度文件，重跑跳过已完成段。

### ⚠️ 4. 断点续跑的进度不能跨轮复用（最危险的「假干活」）
- **现象**：进度文件是裸 `{段号: 条数}`，每轮共用同一个文件 → 新一轮开跑时上一轮的 60 段全标 done → **本班 60 段被整段 skip，形同没扫**，而脚本照样打印 `segments_done=60`，**输出看起来完全正常**（不报错、只是悄悄没干活）。
- **正确做法**：进度文件改成 `{"run_now": <锚点 epoch>, "segs": {...}}`，**跨轮自动重置**（重置时进度与 items 都清空）、旧格式自动重置；只有显式 `--resume` 才沿用上一轮。
- **通用教训**：带「断点续跑」的机制，**进度必须能证明自己属于同一轮**。段号这类隐式身份在锚点漂移后静默失效。凡是「输出看着正常但其实没干活」的路径，优先怀疑进度/缓存的跨轮复用。

### 5. `--owner-ids` 传 open_id 必报 99992361
- **现象**：open_id 是**应用维度**的，跨应用不通用 —— 即使用户自己的 open_id 也会报 `99992361`。
- **正确做法**：`--owner-ids me` 或干脆不传（归属在每条 `display_info` 的「所有者:」里自己筛）。

### 6. 索引收录滞后于录音时间，且发生在扫描过程当中
- **现象**：录音 08:58 完成、09:05 才可查；更糟的是**收工前二次复查又捞出第 3 条** —— 索引是在本轮扫描进行当中才收录的。
- **正确做法**：**收工前必须再独立拉一次**，且用不同时间窗交叉验证（近 90min / 近 6h / 当天段各拉一轮）。一次宽窗复查只覆盖扫描那一瞬间的索引状态。

### 7. 时长字段的位置
- **现象**：想用正则从 display_info 扒时长，按「所有者」切开会拿到空值。
- **正确做法**：**优先从 `meta_data.description` 取**（格式固定：`所有者: x 开始时间: YYYY.M.DD HH:MM:SS 时长: N 分 M 秒`）。小时/分/秒都要单独解析，顺序是 时→分→秒。

### ⚠️ 8. `+detail` 一次最多收 50 个 token
- **现象**：候选 97 个 → 报 `too many tokens`。
- **正确做法**：按 ≤40 一批分批拉。

## 二、去重

### ⚠️ 9. 只查一道会重复归档
- **现象**：只查状态文件 → 漏查档案 frontmatter → 已归档的稿在下一轮被当成新稿再归档一份。
- **正确做法**：**两道必查并集**，任一命中即已处理：
  1. `state.json` 的 `processed` 数组
  2. 档案 frontmatter 的 `minute_token:`
- **可选第三道**（多 agent / 多工具共用时配）：共享登记表 `SENTINEL_REG`、外部已处理目录 `SENTINEL_EXTRA_PROCESSED_DIR`。

### ⚠️ 10. 外部目录的宽松匹配
- **现象**：严匹配 `minute_token[_0-9]*:\s*obcn[a-z0-9]*` 只命中 **15** 个 token，宽松匹配（任意行同时含 "token" 与 "obcn"）命中 **30** 个 —— 字段名变体还有 `妙记token:` / `token:` / `**token**`。漏掉的 15 个里就有外部工具当天处理的一条稿，**只按严匹配查就会给它写一份重复档案**。
- **正确做法**：一律用宽松口径（Python：`if "token" in line.lower() and "obcn" in line` → 收 `re.findall(r"obcn[a-z0-9]+", line)`）。

### ⚠️ 11. 「合同写了 ≠ 代码实现了」
- **现象**：文档里写了三道去重，脚本只实现了两道 → 外部工具处理完的稿落在它自己的目录，两道都看不见 → 每轮把它当未处理的重复归档。
- **正确做法**：**每次改去重口径都要同步改脚本，并实跑验证**。

### 12. 「已登记但档案文件缺失」≠ 出错
- **现象**：看到「state 说已归档、文件却不在」判为「静默失败」并重新拉稿补档 —— 但那条档案可能是用户主动删的。
- **正确做法**：**删除必须留墓碑** —— `state.note` 记一句「⚠️ 用户要求删除，勿再补档」（用共享登记表时同样追加一行）。只删文件不改标记，下次会被拉起来重新补档。

## 三、逐字稿获取

### ⚠️ 13. `--output-dir` 有白名单
- **现象**：指向绝对路径（如档案树 `.state/tmp/`）报 `is outside the built-in allowlist; allowed roots are the current working directory, /tmp, or ~/files`。
- **正确做法**：**先 `cd` 到目标目录再用相对路径**（`cd <scratch> && lark-cli minutes +detail ... --output-dir ./td --overwrite`）。白名单行为随 lark-cli 版本变，脚本里只留一句「先 cd 再用相对路径」。

### 14. 产物目录名带标题原文，shell 遍历会炸
- **现象**：`artifact-<标题>_<token>/` 里标题含空格 —— shell 按空白切词 → `No such file or directory`。
- **正确做法**：用 Python `os.walk` 读，或 `find -print0` + `while IFS= read -r -d ''`。

### ⚠️ 15. 「成功取到」≠「有内容可提炼」
- **现象**：逐字稿可能只有一行乱码（既非中文也非英文，疑似把背景声误识别成外语词）或一个空壳（只有时间头 + 空 Keywords）。
- **正确做法**：**不要跳过 token**（跳过 = 静默失败），**也不要推测补写**（保真红线）—— 按实存内容**如实建档**，档案写明「转写不可辨识」「转写为空壳」，三句话摘要说清为什么没有待办/素材/金句。

### 16. 多路降级的顺序
- **路 1c**：`+detail --transcript`（万能兜底，连无 note_id 的条目也能拉到）
- **路 1b**：normal note 直取 —— `note +transcript` 报 `is not a unified note (note_display_type=normal, verbatim_doc_token=XXX)` 时，**错误信息里的 `verbatim_doc_token` 就是逐字稿 Docx token**，直接喂 `docs +fetch`，不用走路 2/3。近期妙记几乎全是 normal note，此路命中率最高。
- **路 2**：`docs +search "文字记录：<标题关键词>"`（原录音被删时，2091004 不算失败，文字版还在）
- **路 3**：`drive +search "智能纪要 <标题关键词>"` → 读其**底部文字记录区块**
- 验证：转写 > 50 字符且非报错文本才算成功。

### ⚠️ 17. 老妙记的转写会过期
- **现象**：较早的条目多为 `status=1` 且无 note_id（转写数据失效），路 1 不可用。
- **正确做法**：路 2/3 按标题关键词常命中**同名不同日期**的 Docx —— 取回后核对正文「录音时间：YYYY年M月D日」与目标日期一致才可用，否则会错拿别的录音内容。

## 四、档案规范

### ⚠️ 18. 撞名会覆盖旧档案
- **现象**：归档文件名只到「日期+类型+主题slug」，不同批次的同名稿会撞名。直接写就把旧档案覆盖了（旧 token 正文丢失）。
- **正确做法**：**写前先 `ls` 目标目录**，已存在且 token 不同 → 加后缀。批量写完后校验全库 `minute_token` 无重复。
- **顺序**：如果已经覆盖了，要从 git 恢复被覆盖的那份 —— ①先 `git show HEAD:<旧路径>` 取回旧内容写到新后缀名下 ②再把本次新内容改名 ③校验无重复。**先取回再改名，顺序反了旧档案就真丢了。**

### ⚠️ 19. 缺一级标题 = P0
- **现象**：档案只有 `## 三句话摘要` 没有 `# 标题` → 机器校验判「无一级标题」→ P0。实测一个批次 15 份全中。
- **正确做法**：frontmatter 之后加 `# 标题`（取文件名 slug），位置在 frontmatter 之后、`## 三句话摘要` 之前。

### 20. 归档路径要「复制不要凭记忆拼」
- **现象**：目录迁移/改名后，凭手感拼路径会写回旧目录 → 新旧两处各一份，闸门读新的，旧的那份永远不更新、还被 git 当成「删除」。
- **正确做法**：**写档案前先 `ls` 目标目录确认路径存在且含 `.state/`**；目录已冻结/改名的（如 `archive.迁移冻结-*`）不要往里写。

### 21. 超长稿不必全量粘
- **> 2 万字符**：存开头 500 字符样例 + source Docx token + 一行取回命令，档案保持可读、全文随时可取。**长稿也不豁免机器校验**。

## 五、机器校验层（fact_check）

### ⚠️ 22. `--source` 要传合并源文件
- **现象**：传裸 transcript.txt → frontmatter 里的 `minute_token` 长数字字段（如 `obcnXXXX...XXXXXX` 尾段的长数字）被判「原文中找不到」→ P0。
- **正确做法**：`--source` 传「妙记元信息头 + 逐字稿原文」的合并源文件（头写 token/title/开始时间/时长毫秒，正文逐字稿零改动）。

### ⚠️ 23. 正文里写别的档案的完整文件名 = 编造
- **现象**：写 `YYYYMMDD_其他_主题A.md` 这类交叉引用 → 文件名里的 8 位日期数字在逐字稿里找不到 → P0。
- **正确做法**：交叉引用**别写完整文件名**，写成「同批录音里的「主题A」那条」。写其他目录的任务主档文件名同样会撞 → 改成描述性表述。

### ⚠️ 24. 正文里写具体日期数字 = 编造
- **现象**：正文写具体日期+时刻（如「YYYY-MM-DD 06:52 提出」）→ 逐字稿里没有 → P0。
- **正确做法**：时间用「录音时间 XX:XX」表述。frontmatter 的 `note` 里写秒级时间点不 P0（短数字只 WARN）。

### 25. 时间戳别写小数部分
- **现象**：`[00:04:15.700]` → 那串数字在源文件里被正则切成 `15.700` 而找不到 → P0。
- **正确做法**：引用用秒级时间戳 `[00:04:15]`。

### 26. 残留标记规则会误判真实内容
- **现象**：`【待办】` 里的「【待」命中待填占位规则，转写原文里的 `[XXX]` 命中 xxx 占位规则。
- **正确做法**：**这两类不能改原文**（改了违反保真红线）。人工确认是转写原文自带后，重跑校验加 `--allow-residue` 显式豁免——豁免会记入 WARN（不是静默放过），且只应在你确认「原文确实带这个标记」时使用。

### 27. 批量写完要循环跑完全部
- **正确做法**：把 fact_check 写成循环跑完全部文件，**全绿再动 state.json/登记表**。不要逐个手点，也不要因为「格式都一样」就跳。实测一次写 15 份全带着同一个 P0。

## 六、TODO 账本（本版本待办的唯一去向）

### 28. 待办只记本地 TODO.md
- **正确做法**：提炼出的待办记入 `<归档根目录>/TODO.md`，每条带来源（`YYYYMMDD_档案.md` + 录音时间），**不建任何外部任务卡、不派给任何人**。
- 「录音里没说要做任务」→ 不记待办区，归素材（标待确认）。
- 归属是别人的待办（长录音里对方说「我要去做 XX」）→ 不进 TODO.md，档案里注明「对方的事」。

### 29. TODO.md 与档案互为索引
- **正确做法**：TODO.md 每条链回档案文件名；档案的「### 待办」节同样列出条目。销待办时两边一起销，只销一边 = 账实不符。

## 七、汇报纪律（用户当面问时）

### ⚠️ 30. 汇报只给结论
- **正确做法**：第一句是「扫到了 N 条，都是 XX 主题」，不是「我先查了 state.json，然后跑了分段扫，发现接口有 50 条上限……」。底层机制有坑时写成结论里的一小句。收尾给「数量 + 落点 + 需要用户定的」三件，不重述步骤。

### 31. 多条新稿合并成一次回复
- **正确做法**：一次扫描一条回复，不逐条刷屏。

### 32. 无新妙记 → 静默收工
- **正确做法**：不发「没有新录音」之类的填充性输出（噪音即狼来了）。

### ⚠️ 33. 失败必须显式出声
- **现象**：脚本 `print("")` 静默退出 → 接口报错/授权失效彻底隐形，用户只看到「什么都没发生」。
- **正确做法**：失败时输出带原因 + 影响 + 自查命令（`lark-cli auth status --as user`）的报警文本。宁可吵，不可哑。

## 八、状态文件

### ⚠️ 34. `processed` 只放纯 token 字符串
- **现象**：塞进 `{'minute_token':..., 'note':...}` 这种 dict → 脚本用 `set()` 去重，**dict 不可 hash 会让整个闸门班次崩掉报「state.json 读取失败」**。这个坑踩过两次。
- **正确做法**：写 state.json 优先用 `json.load` + append 纯字符串 + `json.dump`，**不要手写整个 JSON**（手写时容易顺手塞进 dict）。要记 note 就写 state 的 `note` 字段或墓碑行。

### ⚠️ 35. `last_scan` 可能是未来时间
- **现象**：上一场 session 写了 `last_scan=09:05` 而现在 `09:01` → 直接当增量窗起点会触发 API 报 `--start is after --end`，**增量窗整段作废**。
- **正确做法**：扫之前先比 now，last_scan > now 就**钳制到 now-5min**。

### ⚠️ 36. 闸门量必须是「未处理集合哈希」，不是累计计数
- **现象**：早期用累计数（seen 只增不减）→ agent 某班归档失败时该 token 已进 seen，下一班 pending 为空 → 累计数不变 → 闸门不再唤醒 → **那条稿永久漏处理**。
- **正确做法**：改成未处理集合哈希（`pending_total` + `pending_sig`）。只要还有没归档的，每班都会唤醒重试；全部归档完 → `pending_sig` 回到基线（空集哈希 `da39a3ee5e6b`）→ 静默。
- **判据始终是「去重并集比对后未处理是否为 0」**，不是闸门数字本身。

### ⚠️ 37. 闸门 pending 看绝对值，不看升降方向
- **现象**：diff 是 `pending_total=2 → 1`，看着像回落，实际是上一班回落 2 + 本班新增 1 —— **净变化为负也藏着一批真新稿**。
- **正确做法**：`pending_total > 0` 一律当真新稿走完整归档流程；`== 0` 才可能是纯回落白唤醒（照常跑完整核对，确认未处理为 0 再静默收工）。连测五次与宽窗分段复查完全一致。

### 38. 回落型唤醒是常态不是异常
- **现象**：「每次上一班归档完真新稿后的下一班」几乎必然来一次回落唤醒（实测 2→0、1→0）。
- **正确做法**：别当异常、别期待「以后就不唤醒了」，每班照常跑完整核对流程。

### 39. 登记（写 state / 登记表）放最后一步
- **正确做法**：**提前登记会让扫描器以为已处理而漏报**。全链路的最后一步才是更新状态。

## 九、并发与幂等

### ⚠️ 40. 动手前先确认没有同类 job 正在跑
- **现象**：深度归档单轮可能跑几十分钟，期间手动又触发一轮扫描 → 两边同时写同一批 token 的档案/状态，**看着像重复归档**。
- **正确做法**：`hermes cron runs <job_id>` 看是否 running。是则**不要并行拉稿/归档/登记**，等它跑完再补漏。

### ⚠️ 41. `cron run` 对正在 firing 的 job 会被拒
- **现象**：`Job is already being fired by the scheduler; not run again.` + `cron resume --at` 报 `Cannot re-arm one-shot over a live fire claim`。
- **正确做法**：**别手动 run** —— 调度器会自己做 catch-up 补跑。resume 后看 `cron status` 的 Next run 是否被重算到正确时间（resume 有时会把 next run 设成过去的时间，状态会报 OVERDUE）。

### 42. 脚本多副本要同步
- **现象**：同一脚本在共享目录和各 profile 的 `scripts/` 各有一份，改一处不同步 → 行为分裂。
- **正确做法**：建议**单一副本 + 软链/配置**。

## 十、时区与时间

### 43. 扫描前实测时区
- **正确做法**：`date +%z`。妙记时间都是北京时间，机器时区漂移时换算后再查，不直接用本地时间。

### 44. 日期以 `date` 命令为准
- **现象**：会话可能跨午夜，会话开始日期不可信。
- **正确做法**：每条稿的归属日期取 `display_info` 的「开始时间」，不是调用日期。

### 45. 午夜前后的录音归属
- **现象**：跨零点录的稿会被算到第二天。
- **正确做法**：按妙记自带的「开始时间」归属，不要用文件 mtime 或调用时刻。

## 十一、批次统一整理（多条同主题）

### 46. 批次要出总览
- **现象**：一次录十几条同主题录音，只交 N 份逐条档案 = 没回答「这些想法拼起来是什么」。
- **正确做法**：**逐条档案照常出，再出一份总览** —— 按层次/模块串起来，指出这是**一个大工程**而非 N 个孤立待办；标出**前置闸门**（哪一步没完成后面不能动）、**贯穿的动机线**、可并行支线；末尾给**建议执行顺序**（先做不依赖闸门的那件）。总览文档同样登记 state.json。方法论见 [references/batch-unified-review.md](./references/batch-unified-review.md)。

### 47. 总览也要登记
- **正确做法**：总览文档写「（总览）」行 + 各 token 行进 state.json，否则下轮扫描会当未处理重复归档。

## 十二、事实与归属

### ⚠️ 48. 提炼里出现转写原文没有的断言 = 致命错误
- **正确做法**：删或标「待确认」。数字、日期、人名、归属一个都不能编。

### ⚠️ 49. 他人分享 ≠ 用户原创
- **现象**：录音里转述的方法论/案例/数据可能**全部来自别人** —— 连说话人原话里的「我/我做的」都可能指原作者。
- **正确做法**：入档注明「他人分享，用户收藏」vs「用户原创」。**归属存疑连带细节存疑**：来自他人分享的内容里的具体名词（活动名、工具名、数据）同样未经确认，标「待确认」。

### 50. 说话人身份不猜
- **现象**：转写默认不打真名，靠内容推断。
- **正确做法**：推断的写「待确认」；明确单一说话人的可定性为本人。

### 51. 长录音里的「信息」很多是对方的
- **正确做法**：朋友闲聊/分享会的八节里，Business/Content 装的是**对方口述的第三方信息**，逐条标注「朋友转述，非用户产出」，其中对方的待办不进 TODO.md。

### 52. 其他流程已消费同一份稿时
- **正确做法**：`grep -rn "<minute_token>" <相关目录>/` 查证它被消化到哪一步 → **仍然要归档**（去重链不能缺），但**不重复产出同一份成品**，档案「来源与处理说明」写明「已由 XX 流程处理（附本地路径）」；成品里的出处/作者信息若不是本条逐字稿说的，必须标明来自哪里。

## 十三、闸门（Hermes cron 零 token 机制）

### 53. 闸门输出必须字节级稳定
- **正确做法**：monitor 脚本输出**字节不变 → 不唤醒 agent**。输出格式里的计数与哈希都必须是「未处理集合」的确定性函数（见 scripts/check_minutes_monitor.py）。

### ⚠️ 54. 去重必须 token 提取，不能整行比对
- **现象**：把登记表**整行**塞进 done 集合、再用**裸 token** 去查 → token 永远匹配不上整行 → 去重完全失效 → 输出变成「窗口内妙记条数」，随 24h 窗口滑动而变 → 闸门常开白唤醒。
- **正确做法**：每道都用 regex 提 token（`re.findall(r"minute_token:\s*(\S+)", text)`）。

### 55. `+search` 默认只回第一页
- **正确做法**：窗口内超过一页必须按 `page_token` 翻页；且 50 条硬截断（见规则 2）意味着宽窗必须分段。实测同窗口一次拉回 15 条、分段拉回 42 条，差的全是当天早上的。

### 56. 改了闸门输出格式必须同步基线
- **正确做法**：用 Hermes 自己的 monitor 状态接口重置基线（别手改 jobs.json），否则格式变化被当成「内容变化」白唤醒一次。注意 scheduler 对脚本输出会去掉尾部换行，基线字节要跟 runner 实跑的一致。
